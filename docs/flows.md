# Product and Agent Flows

## 1. Upload and indexing

```text
User selects files
  -> client validates type/size
  -> API creates upload session
  -> private storage upload
  -> API records checksum and DocumentVersion
  -> API enqueues background DocumentProcessingJob and returns immediately
  -> worker finalizes upload and verifies checksum
  -> worker extracts pages/text
  -> worker chunks content and creates FTS/embedding indexes
  -> worker validates consistency
  -> ready OR failed at a named step with actionable reason
```

The UI must let users continue chatting with already-ready documents while new files index. A failed file should not make the whole conversation unavailable. A document is not chat-eligible until its processing status is `ready`; the UI should show a disabled “Chat” action with the current processing step until then.

The Documents page is the source of truth for processing state. Each document displays step indicators such as `Upload`, `Extract`, `Chunk`, `Index`, and `Ready`, plus current progress, last update, retry, and failure details. Users can leave the page and return later; the job continues on the server. Multiple files are represented by separate jobs or independently trackable child items so one failed file does not hide successful files.

### Indexing record created by the worker

The indexing worker writes an immutable `DocumentVersion`, then creates one `DocumentPage` record per source page and deterministic `DocumentChunk` records linked to those pages. It updates the FTS/vector indexes only after page and chunk records commit successfully. The worker records parser, OCR, chunking, and embedding metadata so an answer can explain or retry how evidence was produced. PDF and DOCX files are in scope; pages or document content that are image-based use OCR, with OCR status and confidence stored in page metadata. A version is `ready` only when its page/chunk records and configured retrieval indexes are consistent.

The worker must be safe to restart at any point. Each step uses the document-version checksum and a step idempotency key; retries do not duplicate pages, chunks, embeddings, or index entries.

## 2. Basic chat flow

```text
User message
  -> authenticate + authorize workspace/document scope
  -> classify as document-grounded question
  -> retrieve relevant passages
  -> generate answer with citations
  -> validate citation presence and that every reference belongs to retrieved authorized chunks
  -> stream answer and quick actions
```

Chat quick actions should include “summarize”, “find key fields”, “create template from this”, and “extract with template”. These actions carry the current document scope and conversation context into the next request.

### Chat response contract

```json
{
  "messageId": "msg_123",
  "text": "...",
  "citations": [
    { "documentId": "doc_123", "page": 4, "label": "Invoice total" }
  ],
  "suggestedActions": [
    { "type": "create_template", "label": "Create a template" }
  ],
  "grounding": "supported"
}
```

Possible `grounding` values: `supported`, `partially_supported`, `not_found`, `not_applicable`.

For a grounded question, the server must not accept a citation that is only a page number generated by the model. The citation must resolve to a stored `chunkId`/`pageId`; otherwise the response is repaired or downgraded to `not_found`. This keeps references accurate after re-indexing and makes the answer auditable.

### Chat/document scope

Users can create multiple chats from the chat list or from a ready document. Each chat selects exactly one document; the selected document ID is stored on the conversation and shown as a fixed scope chip. Questions retrieve only from that document. A document that is still processing cannot start a chat, and grounded questions remain blocked until indexing completes. Attaching multiple documents to one chat is a later feature.

## 3. Basic-flow failure and agentic fallback

```text
Basic workflow starts
  -> input / permission / readiness check
  -> retrieval or direct extraction
  -> schema / citation validation
       |
       +-- success -> persist and respond
       |
       +-- recoverable transient error -> bounded retry
       |
       +-- unsupported/complex case -> JCode agentic workflow
                                  -> search / inspect / normalize / validate
                                  -> success -> persist with fallback metadata
                                  -> failure -> partial or failed result + retry option
```

The UI should say that an advanced recovery path was used only when useful to the user, for example: “I used an advanced document analysis step because the first extraction could not read the table reliably.” It should not expose internal chain-of-thought or hidden prompts.

## 4. Generate a template

Entry points:

- Chat quick action on a selected document.
- Templates page: “Create from document”.
- Blank template builder.

```text
User chooses source document(s) and describes desired fields
  -> JCode proposes field list and JSON Schema
  -> UI shows editable field names, types, requiredness, examples
  -> user previews extraction on one document
  -> validation issues are shown inline
  -> user saves TemplateVersion
```

The template proposal is a draft until the user confirms it. Template generation should preserve user-defined names and must not silently add fields during extraction.

## 5. Single-document extraction

```text
User chooses template + document
  -> verify template version and document ready state
  -> execute schema-constrained extraction
  -> validate JSON Schema
  -> attach evidence and confidence/status per field
  -> render editable result
  -> user accepts or corrects
  -> persist final result and optional review audit
```

Field status examples: `extracted`, `missing`, `ambiguous`, `invalid`, `reviewed`.

## 6. Bulk extraction

```text
User chooses template + document set
  -> review estimated scope and limits
  -> create BulkJob
  -> enqueue idempotent BulkItems
  -> process with bounded concurrency
  -> update progress stream/polling endpoint
  -> show completed, needs review, and failed items
  -> retry selected failures or export valid results
```

Bulk results must be usable even when some documents fail. The export should include row-level status and an error/review column.

## 7. State machine

### Bulk job

`draft -> queued -> running -> completed`

Alternative terminal states: `completed_with_errors`, `cancelled`, `failed`.

### Bulk item

`queued -> processing -> succeeded`

Alternative states: `retrying`, `needs_review`, `failed`, `cancelled`.

### Extraction result

`draft -> validated -> needs_review -> approved`

An approved result is immutable; corrections create a new revision.

## 8. Error UX

Every error needs three parts: what happened, whether work was saved, and the next action.

| Error | User-facing behavior |
|---|---|
| Unsupported file | Explain accepted formats and allow replacing the file |
| Indexing delayed | Keep item queued and show refresh/status |
| No evidence found | Say the answer could not be supported; offer broader document scope |
| Schema validation failed | Show field-level issues and offer repair/review |
| Rate limit/transient provider failure | Keep job state, retry automatically, show retry timing |
| Partial bulk failure | Preserve successful rows and offer retry-failed-only |
| Permission failure | Do not reveal resource existence; show access guidance |

## 9. API surface draft

```text
POST   /v1/uploads
POST   /v1/documents/:id/ready
GET    /v1/documents
POST   /v1/conversations
POST   /v1/conversations/:id/messages
GET    /v1/conversations/:id/events
POST   /v1/templates/proposals
POST   /v1/templates
POST   /v1/templates/:id/extractions
POST   /v1/bulk-jobs
GET    /v1/bulk-jobs/:id
POST   /v1/bulk-jobs/:id/retry-failed
POST   /v1/exports
```

All mutating endpoints should accept an idempotency key where duplicate requests could create work or charges.
